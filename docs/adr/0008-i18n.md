# ADR-0008 — French-first bilingual, YAML translation catalog

**Status:** Accepted · **Date:** 2026-08-09 · **Revised:** 2026-08-09 (adopt the CogitovaSchool YAML catalog pattern) · **Depends on:** ADR-0004

## Context

Congo's official language is French. Travellers, agents and conductors work in French; English matters for the diaspora, for NGO/corporate accounts, and for the engineering team. Everything user-facing must exist in both.

Most bilingual apps are authored in English and machine-translated to French. The result reads like a translation, and in a market where trust is the barrier to a first payment, copy that reads foreign is a conversion problem.

There is a second constraint that rules out the obvious Flutter answer. We have **four surfaces plus a server** (ADR-0004), and the server independently renders user-facing text: SMS receipts, payment-failure notices, disruption alerts, PDF tickets, operator statements. Flutter's ARB / `gen_l10n` is a Flutter-only mechanism — it cannot serve the Dart backend. Using ARB for clients and something else for the server means two catalogs, two review processes, and inevitable drift between the SMS a user receives and the screen they then open.

## Decision

**French is the source and fallback language.** **One YAML translation catalog**, shared by every surface and by the server, following the pattern proven in `CogitovaSchool.Localization` — ported to Dart as `packages/bel_localization`.

### Layout

```
packages/bel_localization/
├─ i18n/
│  ├─ languages.yaml            manifest: default + supported languages
│  ├─ fr/                       SOURCE language
│  │  ├─ common.yaml            shared vocabulary: actions, labels, states
│  │  ├─ pages/                 one file per screen/feature
│  │  │   onboarding.yaml  search.yaml  seatmap.yaml  payment.yaml
│  │  │   ticket.yaml  refund.yaml  disruption.yaml  console.yaml  admin.yaml
│  │  ├─ enums/                 domain enum labels
│  │  │   booking.yaml  payment.yaml  disruption.yaml  roles.yaml
│  │  ├─ errors/                error-code → message, keyed by wire code
│  │  ├─ messages/sms.yaml      outbound SMS (length-sensitive)
│  │  ├─ emails/transactional.yaml
│  │  ├─ notifications/push.yaml
│  │  └─ reference/             cities, amenities, payment rails
│  └─ en/                       same tree, mirrored
└─ lib/                         loader + translator
```

### Mechanics (mirroring the reference implementation)

- **Nested YAML, flattened at load** to dotted keys: `payment.waiting.title`, `common.actions.cancel`, `sms.paymentConfirmed.body`. Nesting is for authoring comfort; lookup is a flat `Map<String,String>`.
- **Loaded once at startup**, immutable in memory. On the server it is a singleton; in Flutter it is bundled as an asset and parsed once.
- **Fallback chain: requested language → default (`fr`) → the key itself.** Lookup **never throws**. A missing translation degrades to French, then to a visible key — never to a crash and never to a blank.
- **Interpolation with named placeholders**: `"Départ à {time} depuis {station}"`. Never string concatenation — French word order is not English word order.
- **Plurals** as `key.{category}` with an `other` fallback, using proper CLDR categories. French and English differ at zero (`0 place` is *singular* in French, `0 seats` is *plural* in English) — the exact thing machine translation gets wrong.
- **Enum labels** under `enum.{TypeName}.{Value}`, so a `PaymentState` or `DisruptionCause` renders correctly on every surface without a switch statement in the UI.
- **Content hash** over the whole catalog, exposed as an ETag so web consoles cache aggressively and bust correctly on deploy.
- **The server never sends user-facing prose.** APIs return `message_key` + params (`02-architecture.md` §6); each surface renders it in the reader's own language. The one exception is SMS, which the server must render itself — using the same catalog, in the recipient's stored language.

### Why YAML over ARB

| | ARB / gen_l10n | YAML catalog |
|---|---|---|
| Works in the Dart backend | ❌ | ✅ |
| One catalog for app + web + server + SMS | ❌ | ✅ |
| Namespacing / file-per-feature | flat, one file per locale | nested tree |
| Readable diffs in review | poor (one huge JSON) | good |
| Comments for translators | metadata only | native `#` comments |
| Compile-time key safety | ✅ generated getters | ⚠️ recovered via codegen (below) |

The one real advantage ARB has is compile-time key checking. We get it back with a small build step that generates a `K` constant class from the **French** tree (`K.payment.waiting.title`), so a typo is a compile error and a renamed key breaks the build everywhere at once.

### Formatting is locale data, not translation

| Concern | Rule |
|---|---|
| **Currency** | `9 000 FCFA` — narrow no-break space, symbol after, in `fr`. `XAF 9,000` in `en`. Zero decimals always. Always via `Money.format(locale)`, never hand-built. |
| **Dates** | `sam. 15 août` (`fr`) · `Sat, 15 Aug` (`en`). Never `MM/DD` — ambiguous and wrong for this locale. |
| **Time** | 24-hour in both. Departure times are never am/pm. |
| **Phone** | `+242 06 12 34 56`, grouped in pairs — how Congolese numbers are read aloud. |

`culture` in `languages.yaml` drives `intl` formatting only. It is **never** used for string lookup — that is `code`.

### Layout consequences

French runs **15–25% longer than English**. Every component is designed and reviewed against the **French** string, not the English one. No fixed-width buttons. A golden-test suite renders key screens in both locales at 0.85×, 1.0× and 1.3× text scale; overflow fails the build.

### Governance

- Translations live in git, reviewed like code. For two languages a SaaS TMS is pure overhead — revisit at four.
- CI fails on: a hardcoded user-facing string literal in a widget, a key present in `fr` but missing in `en`, an unused key, or a placeholder mismatch between locales.
- One named owner for French copy quality. This is a real role, not a side task.

### Beyond FR/EN

The manifest supports more languages at zero architectural cost — adding `ln` is a folder. **Lingala and Kituba are candidates for onboarding, SMS and the ticket only** — the highest-anxiety moments — rather than the whole app, since technical vocabulary in those languages is not settled and a half-translated app reads worse than a French one. Decide with real users, not from a desk.

## Consequences

We port and maintain ~200 lines of catalog loader instead of using a framework mechanism — cheap, and it is the price of one catalog serving five runtimes. The `K` codegen step must run before analysis in CI or key errors surface late. In exchange, an SMS, a push notification, a PDF ticket and a screen all draw from the same reviewed French sentence.
